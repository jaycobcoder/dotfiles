# 설계 결정

이전 프로젝트에서의 실수와 현재 설계 판단의 근거를 기록한다. 규칙 뒤에 있는 *이유*를 담은 문서이므로, 새 규칙을 적용하려는 것이 아니라 의도를 이해하기 위해 읽는다.

## 1. 의존성 방향을 너무 엄격하게 따름

**문제**: "도메인은 인터페이스만 두고, 인프라스트럭처가 구현한다"를 모든 곳에 적용했다. `application`이 `domain`만 의존하도록 강제하면서 과도한 간접화가 생겼다.

**현재 판단**: `application`은 `infrastructure`를 직접 의존한다. 인터페이스–구현 분리는 실제로 교체 가능성이 있는 곳에만 적용한다.

→ [architecture.md](architecture.md) > 핵심 규칙 참고.

## 2. 같은 도메인 엔티티를 유즈케이스별로 분리

**문제**: "목장 기록의 목장소"와 "079 일정의 목장소"를 별도 클래스로 분리했다. 같은 도메인 개념이 여러 클래스로 흩어지면서, 변경할 때마다 분리된 복사본을 전부 손대야 했다. 최악의 실수였다.

**현재 판단**: 하나의 도메인 개념은 단일 JPA Entity로 관리한다. 유즈케이스별 분리를 금지한다.

→ [architecture.md](architecture.md) > 엔티티 전략 참고.

## 3. 레이어드로 충분한데 MSA를 적용

**문제**: 1~3명 규모의 팀에 MSA를 도입하여 프로젝트가 비대해졌다. 서비스 간 통신, 배포 파이프라인, 데이터 정합성 등 부수적 복잡도가 핵심 비즈니스 로직보다 커졌다.

**현재 판단**: 모놀리식 레이어드 아키텍처를 유지한다. 서비스 분리는 팀 규모 확대, 독립 배포 필요 등 명확한 근거가 있을 때만 검토한다.

## 4. 이벤트 드리븐으로 흐름 추적 불가

**문제**: 이벤트 발행 → 이벤트 발행 → 처리로 3중 뎁스가 생겼다. 의존성 관리는 편해졌으나, 로직 흐름 추적이 사실상 불가능해졌다. 디버깅과 장애 대응이 극도로 어려워졌다.

**현재 판단**: 이벤트 기반 개발을 금지한다. 모든 로직 흐름은 Master Service에서 명시적으로 호출하여, 코드만 읽으면 전체 흐름이 드러나게 한다.

→ [architecture.md](architecture.md) > 서비스 구조 참고.
